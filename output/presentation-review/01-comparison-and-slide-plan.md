## 2. จุดที่รายงานล่าสุดยังสรุปไม่ตรงกันเอง

ต้องแยกประเด็นเหล่านี้จากข้อผิดพลาดของสไลด์ เพราะไม่ควรนำข้อความล่าสุดทุกบรรทัดไปใช้โดยอัตโนมัติ

| ประเด็น | จุดที่ไม่ตรงกัน | วิธีใช้ในการนำเสนอ |
|---|---|---|
| React Native กับ Flutter | บทคัดย่อยังเขียน React Native แต่บท 3 ตารางซอฟต์แวร์และผล Frontend ระบุ Flutter/Dart | ใช้ Flutter/Dart ตามเนื้อหาวิธีพัฒนาและหลักฐานทดสอบ พร้อมบันทึกให้แก้บทคัดย่อภายหลัง |
| Machine Learning | บท 3 และตารางทฤษฎีบท 4 บางข้อความเขียนเหมือนใช้ Decision Tree/Random Forest แล้ว แต่บท 5 บอกยังไม่พัฒนา | ใช้สถานะ “ML งานต่อยอด” และนำเสนอเฉพาะการปรับตามข้อมูล/เงื่อนไขที่มีผลตรวจสอบ |
| Strava/Health Connect | กรอบแนวคิดและภาพสถาปัตยกรรมมีการเชื่อมข้อมูล แต่บท 5 ระบุ Strava ยังไม่พัฒนา ส่วน Health Connect ไม่พบผลยืนยันพร้อมใช้ | Strava อยู่ในอนาคต ส่วน Health Connect งดอ้างเป็นฟังก์ชันทดสอบแล้ว |
| เพื่อนสองบัญชี/ภาพโปรไฟล์/เหรียญไม่พอ | ข้อจำกัดของชุด API ในหัวข้อ 4.5 และบท 5 ยังระบุไม่ได้ตรวจ แต่หัวข้อ 4.6 มี FT-07, FT-08–10, FT-14 ตรวจผ่านแล้วในเส้นทางแอปกับ API จริง | นำเสนอว่า “มีหลักฐาน Integration Test เพิ่มแล้ว” โดยไม่เปลี่ยนความหมายว่า API collection ชุดเดิมตรวจครบ และไม่ขยายผลถึงทุกกรณีผิดพลาด |
| คลับ | บท 5 บอกสิทธิ์สมาชิกยังไม่ครบ แต่ FT-11–13 ตรวจสร้าง ค้นหา ขอเข้า และอนุมัติแล้ว | นำเสนอ workflow ที่ผ่านได้ แต่การโอนหัวหน้า เตะสมาชิก และเปลี่ยนบทบาททุกแบบยังต้องตรวจเพิ่ม |
| Beginner Weekly Cap | สไลด์ 25 ระบุ Easy ≤3 และ Long ≤1 ผล FT-02 ใช้ Easy 3 วันกับ Long 1 วัน แต่หัวข้อ 4.2 ยังไม่ระบุ Cap ของ Beginner โดยตรง | ไม่ใช่ข้อขัดแย้งที่ยืนยันแล้ว คงได้โดยอ้างขอบเขตตัวอย่าง FT-02 และไม่ขยายเป็นกฎของทุกระดับ |
| Leaderboard | ภาพหน้าจอ/คำอธิบายบท 4 มีอันดับรายสัปดาห์ แต่บท 5 ยังไม่มีผลทดสอบครบและเสนอให้กำหนดกติกาเพิ่ม | แสดงเป็นหน้าที่พัฒนา/ออกแบบได้ แต่ไม่ติดป้าย “ผ่านทดสอบครบ” และไม่ใช้เป็นหลักฐานว่าระบบสังคมทั้งหมดเสร็จ |
| Story Mode | ปรากฏในขอบเขตและทฤษฎี แต่ผลทดสอบล่าสุดไม่ได้ยืนยันทุกเส้นทางของ Story Mode | เก็บเป็นแนวคิดหรือส่วนต้องยืนยันเพิ่ม ไม่ยกขึ้นเป็นผลสำเร็จหลัก |
| เครื่องมือทดสอบ | ตารางสรุปวิธีวิจัยบางจุดยังมี Jest/Mocha แต่ผลจริงระบุ Node.js test runner และ Flutter Integration Test | ชื่อเครื่องมือบนสไลด์ควรตามผลการทดสอบจริง |

หลักในการคัด: ใช้ผลทดสอบรายละเอียดอธิบายสิ่งที่ตรวจได้จริง ใช้บทสรุประบุขอบเขตที่ยังไม่ทำ และเมื่อสองส่วนไม่ตรงกันให้ระบุความต่างของชุดทดสอบแทนการเหมารวม

**ต้องอยู่ในสไลด์หลัก:** ข้อมูลที่ใช้ปรับแผนโดยไม่อ้าง ML, สถานะ Strava, ขอบเขต Android, เส้นทางตั้งแผนจนรับรางวัล, ตัวอย่างเพื่อน/คลับ/ร้านค้า, ผล Backend และ Frontend แยกกัน, ข้อจำกัดและงานต่อยอด

**เก็บของเดิมและปรับให้อ่านง่าย:** ที่มา วัตถุประสงค์ SDT/BCTs ขั้นตอนวิจัย 5 ขั้น แผนฝึก 3 ระดับ และความต่าง Main Quest/Side Quest เนื่องจากยังสอดคล้องกับรายงาน

**เก็บเป็นสไลด์สำรอง/เอกสารตอบคำถาม:** UML ทั้ง 25 กรณี, Data Dictionary 41 ตาราง, รายการ Side Quest ยาว, ตารางทดสอบทุกกรณี, Coverage รายไฟล์, เงื่อนไข Taper/Race/Threshold ทั้งหมด และรายละเอียด HTTP 401/404

**ยังไม่ควรใช้เป็นผลสำเร็จ:** ลดการบาดเจ็บจริง เพิ่มระยะทาง 20% รักษาผู้ใช้ 40% พึงพอใจ 3.5/5 ผ่าน UAT ทั้ง 88 กรณี ML พร้อมใช้ และนำเข้า Strava ได้ เพราะยังไม่มีหลักฐานผลตามคำกล่าวเหล่านี้ในรายงานที่ตรวจ
